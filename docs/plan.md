# Car-Rental AI Assistant — план і дорожня карта

Документ для двох аудиторій: **нас** (що будуємо і чому) та **власника/керівника**
(що це дає бізнесу і куди росте). Розділ 7 — бізнес-мовою, без техніки.

---

## 1. Проблема

- Бронювання й перша лінія підтримки у багатьох прокат-компаній — **повністю ручні**:
  типовий канал звернень (сайт/месенджер) веде живий менеджер, без автоматизації.
- Часто **немає онлайн-бронювання і калькулятора ціни**: заявка = форма «ім'я + телефон»
  → менеджер передзвонює. Прайс — статична таблиця.
- Наслідок: менеджер вручну рахує ціну по сітці, повторює одні й ті самі відповіді
  (застава / документи / пробіг / виїзд за кордон), втрачає ліди вночі та в пік.

Це болить у двох відділах одразу: **продажі** + **робота з клієнтами**.

## 2. Рішення — архітектура «драбина»

Не один двигун, а три шари. Кожен вмикається там, де він **найдешевший і найточніший**.

```
Повідомлення клієнта
        │
        ▼
  [ Розуміння наміру ]
   Фаза 0: keyword-правила   ──(пізніше)──►  Фаза 2: ML-класифікатор
        │
        ├─ FAQ?    → відповідь із бази ПРАВИЛ (факти з сайту, 0 галюцинацій)
        ├─ Ціна?   → детермінований КАЛЬКУЛЯТОР (реальна тарифна сітка)
        ├─ Бронь?  → збір слотів → теплий лід менеджеру
        │              └─(пізніше Фаза 2)─► ML-СКОРИНГ ліда (пріоритет)
        └─ Складне / скарга → LLM або ескалація людині
        │
        ▼
   [ Лог кожного ходу → ML-ready датасет ]   ← фундамент під Фазу 2
```

**Принцип: rules-first.** Факти й ціни — це правила (вигадати не можна). LLM — лише
для розуміння вільної мови. ML — лише там, де **даними доведено**, що він точніший за
правила. Це захист від «AI заради хайпу»: кожен складніший шар має заслужити місце
вимірюванням.

## 2б. Операторська консоль (human-in-the-loop)

Бот не замінює менеджерів — він **підсилює** їх. Операторська Telegram-група працює як
«міст»: бот дублює кожен діалог у **окрему вкладку (тему)** на клієнта, і менеджер
будь-коли перехоплює розмову.

- **Вкладка на діалог** — чистий бек-офіс замість спам-потоку.
- **Тихе дзеркало + гучні тривоги** — рутина без звуку; пінг зі згадкою лише коли
  потрібна людина (лід / бот не зміг / прохання людини / скарга). Захист від «казки про
  вовка»: пінгу довіряють, бо він рідкісний.
- **Перехоплення/повернення** — бот замовкає, менеджер веде сам, потім повертає боту.
- **Чесність із клієнтом** — підпис «Менеджер …» і привітання при вступі людини; клієнт
  завжди знає, бот це чи людина.
- **Картка клієнта** (закріплена, авто-заповнення + нотатки `//`) — увесь контекст
  діалогу з одного погляду.

Зв'язок із ML: кнопка «перехопити» та фідбек у картці — це **майбутні мітки** (де бот не
впорався). Тобто консоль не лише обслуговує сьогодні, а й годує датасет для Фази 2.

## 3. Фази впровадження

### Фаза 0 — тестовий бот (зараз)
- ✅ Rules: калькулятор ціни + база FAQ + слот-філінг бронювання (готово, тестовано).
- ✅ Операторська консоль: вкладки, перехоплення, підпис, картка, тривоги (розділ 2б).
- ✅ Інструментування під ML з ходу №1 (див. розділ 4 і 5).
- ✅ Регламент для менеджерів (`docs/operator-guide.md`).
- ⏳ LLM-ескалація (код є, вмикається ключем OpenRouter).
- ⏳ One-pager власнику (before/after + цифри).

### Фаза 1 — у роботі (перші тижні після запуску)
- Збір реальних діалогів + фідбек менеджерів.
- Тюнінг FAQ-бази й порогу ескалації на реальних формулюваннях.
- Метрики: % авто-закритих, % ескалацій, час відповіді.

### Фаза 2 — ML (коли назбирано достатньо даних, орієнтовно 6-12 міс)
ML **не вмикається за графіком — вмикається за обсягом і доказом**. Кандидати за пріоритетом:
1. **Скоринг лідів** — передбачити, який лід конвертує. Мітка = фідбек менеджера
   («забронював / злився»). Найцінніше: прямо впливає на гроші.
2. **Класифікатор намірів** — замінює keyword-правила, коли реальна «брудна» мова
   накопичена. Окупається швидше (більше сигналу на діалог).
3. **Тюнінг порогу ескалації** — вчити з даних замість хардкоду.

> FAQ-відповіді **ніколи не стають ML** — факти знають, а не передбачають.

**Умова промоції будь-якого ML-кроку:** на held-out (відкладених даних) метрика б'є
простіший baseline (правила/LLM). Інакше крок не йде в прод. Методологія — як у
walk-forward валідації: тестуємо на майбутньому, якого модель не бачила.

## 4. Дані як актив (чому логуємо з дня-1)

ML завтра можливий лише якщо дані пишемо сьогодні. Тому кожен хід бота зберігається у
структурі, придатній для тренування:

| Поле | Навіщо |
|---|---|
| `ts`, `user_id`, `session_id` | звʼязати діалог |
| `message` | сире повідомлення клієнта |
| `intent_rules` | що вирішили правила |
| `intent_confidence` | впевненість правил (для тюнінгу порогу) |
| `answer_source` | rules / llm / human |
| `quote` (якщо ціна) | яке авто/дні/сума |
| `outcome` | завершення: лід зібрано / злився / ескалація |
| `manager_feedback` | **мітка від менеджера** — забронював? правильна відповідь? |

`manager_feedback` — найцінніше поле: це **ground truth** для майбутнього ML. Без нього
даних для скорингу не буде.

**Меседж власнику:** бот не просто відповідає — він **накопичує датасет**, на якому
згодом розумнішає. Кожен діалог робить систему точнішою. Це актив, що росте.

## 5. Як міряємо ефективність

- **Авто-резолюшн:** % питань, закритих без людини.
- **Rules vs +LLM:** скільки закрили самі правила, скільки додав LLM (доводить, що
  LLM не зайвий, але й не несе всю вагу — точність + вартість під контролем).
- **Час першої відповіді:** бот = секунди проти ручних хвилин/годин.
- **Фаза 2 (ML):** held-out метрика проти baseline; без переваги — не впроваджуємо.

## 6. Чесні ризики й обмеження

- **Обсяг даних.** Для типової прокат-компанії (сотні клієнтів/міс ≈ 3-6к лідів/рік)
  для ML це скромно. Надійний скоринг — горизонт 6-12 міс, приріст поступовий. На малих
  даних ML переобучується й програє правилам. Тому Фаза 2 — за доказом, не за датою.
- **Якість даних.** Якщо джерела суперечать (напр. пробіг у прайсі vs у FAQ) — перед
  запуском узгодити з компанією; бот стає єдиним джерелом правди.
- **LLM-галюцинації.** Знижені тим, що факти/ціни йдуть з правил, не з LLM.
- **Ескалація.** Бот має чесно віддавати складне людині, а не вигадувати.

## 7. Що це дає власнику (бізнес-мовою)

- Клієнт отримує **миттєву** відповідь і ціну 24/7 — без черги до менеджера.
- Менеджер звільнений від повторюваних питань → працює з **теплими** лідами.
- Жодних «вигаданих» цін: бот рахує строго по вашому прайсу.
- Система **навчається на ваших даних**: що довше працює — то точніша, і завтра
  пріоритезує лідів, які реально бронюють.
- Старт малий і дешевий (Telegram, без переробки сайту), росте поетапно й **під
  контролем цифр** — без переплат за хайп.
